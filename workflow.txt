LOAD-BEARING — do not revert without reading
================================================================================

1. BALANCE IS DERIVED, NEVER STORED.           src/utils/ledger.ts
   `accounts.balance` and `accounts.highest_balance` still exist (NOT NULL) but
   are written once at creation and read by NOTHING. Do not put them back into a
   display path. Balance = size + realised P&L − withdrawals, and a day's trades
   take precedence over a day's session summary so logging both cannot
   double-count.

2. THE TRADING DAY IS LOCAL, NEVER UTC.        src/utils/tradingDay.ts
   Never use `toISOString().slice(0, 10)` to get a date. That is the UTC day and
   it files every evening US session on the following day. `trades.date` is
   derived from `entry_time` on READ, so pre-fix rows group correctly too.

3. DELETION IS SERVER-SIDE AND REVERSIBLE.     src/db/accountDeletion.ts
   The browser cannot delete an auth.users row or a Storage object. Do not add a
   client-side erasure path. The 30-day window is a DATABASE DEFAULT, not a
   client value — that is deliberate, so a skewed clock can't shorten it.

4. NEW SHADCN PAGES GO OUTSIDE `appSurface`.   src/App.tsx
   theme.css's element rules are unlayered and beat Tailwind's layered utilities
   regardless of specificity. Inside the wrapper, `variant="destructive"` renders
   in the legacy grey.

5. LIST QUERIES GO THROUGH selectAll().        src/db/paginate.ts
   A bare `.select('*')` silently truncates at PostgREST's 1000-row `max-rows`.
   No error, no warning — the 1001st trade just stops existing.

6. THE TEST SUITE PINS TZ.                     src/test-setup.ts
   America/New_York. A day-boundary test that runs in UTC proves nothing,
   because local and UTC agree there.

## 2026-09-11 — Correctness: the two-ledger bug
================================================================================
WHAT    One definition of account balance, derived from trades/sessions/payouts.
WHY     There were two, and they never agreed. `accounts.balance` was a stored
        column mutated by logSession() and recordPayout() but NOT by logging a
        trade. `accountBalanceSeries()` computed size + cumulative trade P&L and
        ignored both sessions and that column. DashboardPage handed one to the
        chart and the other to the header of the SAME tile — so the curve and the
        number above it were drawn from different ledgers. A user who only logged
        trades watched the curve climb while the header stayed pinned at their
        starting allocation.
        Two smaller inconsistencies in the same four lines: the curve summed only
        accounts that had traded, while the header summed every account in the
        filter.
HOW     utils/ledger.ts: balance = size + realised P&L − withdrawals. A session
        contributes P&L only on a date with no logged trades for that account, so
        logging both cannot double-count and a user can switch styles mid-account.
        logSession() and recordPayout() no longer write back to the account — both
        were untransacted read-modify-writes from the browser.
        Manual Balance / Highest Balance inputs removed from Edit Account (they
        would silently revert the moment anything was logged); replaced with a
        read-only derived display and an editable Starting size.

## 2026-09-11 — Correctness: the trading day was UTC
================================================================================
WHAT    Day grouping now uses the trader's local calendar day.
WHY     `trades.date` was `entryTime.slice(0, 10)` — a slice of a UTC ISO string.
        Verified by execution:
            local Jan 15 20:30 ET → stored date 2026-01-16  (wrong)
                                  → actual local date 2026-01-15
        The CME session opens 18:00 ET, so for a US futures trader this misfiled
        most of the session, every day. It affected the calendar heatmap, daily
        P&L, the equity curve, weekday stats and the insights range filter.
        The correct helper already existed (utils/timezone.ts, written for FMP
        candles) and had never been applied to the more important case.
HOW     utils/tradingDay.ts. `trades.date` is derived from `entry_time` on READ
        as well as write, so pre-fix rows group correctly with no backfill — and
        a backfill couldn't be right anyway, since SQL doesn't know the user's
        zone.
        Also fixed: TradeDetailPanel printed the UTC date while the journal
        grouped by local; rangeForPreset's Date round-trip (correct only by
        accident — both halves were UTC and cancelled).
        Hardened dailyPnlSeries/weekdayStats to drop unreadable dates: an empty
        date reached WEEKDAY_NAMES[NaN] and rendered the literal string
        "undefined" as a weekday. Found by browser smoke test, not by reading.
FILES   + src/utils/tradingDay.ts, tradingDay.test.ts, src/test-setup.ts

## 2026-09-11 — Correctness: CSV import corrupted data three ways
================================================================================
WHAT    Rewrote the importer; it now refuses to guess.
WHY     All three verified by execution.
        1. DIRECTION INVERTED. `sideRaw.startsWith('b')` meant:
               "Buy" → long   "Long"  → SHORT   (wrong)
               "Sell"→ short  "Short" → short
           Any export using Long/Short imported EVERY trade as short. The P&L came
           from the broker's own column so nothing looked wrong — only the
           direction, the long/short split, and every pattern built on them.
        2. US DATES LANDED TWO YEARS OUT. Slash dates were assumed DD/MM/YYYY:
               "07/25/2026 14:30" → parsed as month 25 → Fri Jan 07 2028
        3. BROKER TIMEZONE IGNORED. Timestamps were read in the IMPORTER's local
           zone; MT4/MT5 stamps are broker-server time (usually GMT+2/+3).
        Plus: `Number("1,234.56")` → NaN, and Postgres accepts NaN into a numeric
        column, which turns every dashboard aggregate into $NaN.
HOW     Date order is PROVEN from the file (a day above 12 proves day-first). If
        every value is ambiguous the dialog asks and blocks import. A file proving
        both orders is rejected outright. Broker-timezone selector added.
        parseNumber handles US and European separators, currency symbols and
        parenthesised negatives, returning null rather than NaN. Rejected rows now
        carry a row number and a reason instead of a bare count.
FILES   M src/features/trades/csvImport.ts (+ .test.ts, 7 → 31 tests)
          src/features/trades/components/ImportTradesDialog.tsx (+ .module.css)
RISK    Do not restore a default date order. Guessing is the bug.
DEPLOY  none

## 2026-09-11 — Privacy: deletion, storage, and an export leak
================================================================================
WHAT    Account deletion is now a 30-day reversible request, completed
        server-side. Uploaded images are actually deleted. Fixed a leak in the
        JSON export.
WHY     Three separate failures:
        · THE PROFILE DELETE WAS A SILENT NO-OP. eaglecapital_profiles had no
          DELETE policy. With RLS on, a delete that matches no visible row is not
          an error — PostgREST reports success. A "deleted" account kept a
          username derived from the user's email local part, readable by EVERY
          signed-in user via the "read profiles" policy.
        · NO IMAGE WAS EVER DELETED, ANYWHERE. There was not one
          storage.remove() call in the codebase. Playbook and report-card
          screenshots survived deleting the example, the playbook, and the whole
          account — in a PUBLIC bucket, at URLs that still resolved.
        · THE EXPORT LEAKED EVERY USER'S PROFILE. exportAllData() ran
          `.select('*')` on eaglecapital_profiles, whose policy is
          `using (auth.role() = 'authenticated')`. That returns EVERYONE's rows.
          Every JSON export contained every user's id and username. Now filtered
          to the caller.
HOW     Deletion records an intent + a purge date. The window is a DATABASE
        DEFAULT (now() + 30 days) with a CHECK clamping it to 29–31 days, so a
        client with a skewed or hostile clock cannot shorten it. Requesting twice
        keeps the original date rather than restarting the clock. Cancelling is a
        DELETE of the row. A banner on every page offers "Keep my account".
        The purge Edge Function (service-role) does what the browser cannot:
        walks Storage recursively (report-card images live in a subfolder that a
        non-recursive list would miss), deletes all 15 tables, then the
        auth.users row. It deletes the request row LAST, so a mid-way failure
        leaves the job queued rather than silently dropped.
        copier_links added to the export list — it had been missing.
FILES   + src/db/accountDeletion.ts (+ .test.ts)
        + src/features/settings/DeletionBanner.tsx
        + supabase/functions/purge-deleted-accounts/index.ts
        M src/db/userData.ts (deleteAllUserData REMOVED — see the comment there)
          src/lib/storage.ts (pathFromPublicUrl, deleteImagesByUrl)
          src/db/{playbooks,playbookExamples}.ts, src/features/settings/SettingsPage.tsx
          src/App.tsx, supabase/schema.sql, src/landing/content.ts
RISK    HIGH. See LOAD-BEARING #3.
